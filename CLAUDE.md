# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

This is a 100% static app: vanilla HTML/CSS/JS, **no dependencies, no build step, no bundler, no package.json**.

- **Run it**: open `index.html` directly in a browser (or serve the folder with any static server).
- **Lint/typecheck**: none configured — there is no tooling to run.
- **Tests**: no test framework in the repo. `js/solver.js` is the one pure, dependency-free module (it takes a `state` object and returns a result — no DOM access), so it's the only thing practical to test outside the browser. It ends with `if (typeof module !== 'undefined' && module.exports) module.exports = Solver;`, so it can be exercised from Node without touching the rest of the app:
  ```js
  const Solver = require('./js/solver.js');
  const res = Solver.solve(state); // state shape: see below
  ```
  When changing the solver, write a throwaway Node script that builds a `state` and asserts on `res.ok`/`res.schedule`/`res.message` rather than trying to test through the UI. For non-trivial solver changes, also fuzz-compare against `git show <prev-rev>:js/solver.js` on randomized instances to catch regressions in feasibility verdicts (false "impossible" is the dangerous failure mode) — this has caught real issues before.

## Architecture

No modules, no build: every file in `js/` attaches its API to a **global object** and is loaded via plain `<script>` tags in `index.html`, in a load-bearing order (`storage.js`, `solver.js`, then `js/ui/core.js` first among the UI files, `js/ui/swap.js` and `js/app.js` last). Getting this order wrong breaks the app silently.

- `js/storage.js` — `Storage` global: localStorage persistence, JSON import/export, `defaultState()`.
- `js/solver.js` — `Solver` global: schedule generation, a **pure function** (`Solver.solve(state) -> {ok, schedule, message}`) with no DOM dependency. See "Solver algorithm" below.
- `js/ui/core.js` — defines the `UI` global (state, `init()`, `renderAll()`). Every other `js/ui/*.js` file extends the same `UI` object via `Object.assign(UI, {...})` — they are not separate modules, just namespace-split source files for one object.
- `js/ui/tabs.js`, `io.js`, `config.js`, `profs.js`, `constraints.js`, `schedule.js`, `swap.js` — one file per tab/feature of the `UI` object (Configuration, Professeurs & dispos, Contraintes, Emploi du temps, plus import/export and cell-swap interaction).
- `js/app.js` — entry point: loads state via `Storage`, calls `UI.init(state, saveCallback)`, wires the theme toggle. `UI.init` re-renders and calls `onChange` (→ `Storage.save`) after every user edit — there's no separate "save" action, state is persisted continuously.

### State shape

```js
{
  config: { classes, subjects, slots, days, openSlots },  // openSlots[day][slot] = true -> il y a cours à ce moment-là (pour tout le monde)
  volumes: { "classe|matière": heures },          // toutes les semaines
  volumesA: { "classe|matière": heures },         // EN PLUS de volumes, uniquement les semaines A
  volumesB: { "classe|matière": heures },         // EN PLUS de volumes, uniquement les semaines B
  profs:   [{ id, name, subjectClasses: { matière: [classes] }, availability: [jours][slots] }],
  constraints: {
    pins:     [{ id, subj, classes: [...], day, slot, profId? }],           // créneau exact imposé
    groups:   [{ id, subj, classes: [...] (>=2), hours, profId? }],          // classes partagent des heures, mais SANS créneau imposé — le solveur choisit
    spread:   [{ id, subj, classes: [...] }],                                // par classe listée : jamais 2h de cette matière le même jour, ni jour ni créneau imposé
    meetings: [{ id, name, profIds: [...] (>=2), classes: [...] (0+), hours, subj? }], // TOUS les profIds obligatoires simultanément (pas un choix parmi éligibles) ; subj optionnel = décrémente le volume des classes listées (cours co-enseigné) ; classes vide = réunion pure sans classe
  },
  options: { noGapsForStudents, solverTimeBudgetMs?, solverMaxIter? },
  schedule: { "classe|jour|slot": { subj, profId, profIds?, pinned?, meeting? } | { weekA?: {...cell}, weekB?: {...cell} } } | null,
  savedSchedules: [{ id, name, date, schedule, message }], // versions gardées de côté (UI, onglet Emploi du temps) — jamais touchées par une nouvelle génération ; max 15, imposé côté UI
}
```
A `schedule` cell is normally the flat shape (one box, applies every week — unchanged). A cell with `weekA`/`weekB` instead means it *alternates*: what's taught there on A-weeks differs from B-weeks (see "Semaine A/B" below) — the two shapes never mix at the same key, so `cell.weekA || cell.weekB` is an unambiguous discriminator used throughout the UI (`UI.cellDescriptor` in `js/ui/schedule.js`) to decide whether to render one box or two.
`schedule` keys and pin/session lookups throughout the codebase use string-concatenated composite keys (`"cls|day|slot"`, `"profId|day|slot"`) rather than nested objects — grep for the `|` template-literal pattern when tracing how a cell is read or written.

There is no "day off" toggle anymore (the old `config.activeDays: boolean[]` was removed) — closing time is per-cell via `config.openSlots[day][slot]`, so a half-day closure (e.g. Wednesday afternoon) doesn't require painting every prof unavailable by hand, and a new prof added later is correctly closed there by default instead of silently defaulting to available. `buildContext`'s `isOpen(d, s)` is the single source of truth for this; `solve()` additionally marks closed cells busy for every class/prof up front (in the same block that applies pins) so the hot-path search functions (`candidatesFor`/`domainSize`) never need their own `isOpen` check — but `availCountFor`, Check 2/2bis, and `repair()`'s candidate loop each read `isOpen` explicitly, since they run before that busy-marking exists or maintain their own separate occupancy model. `UI.migrateState()` (`js/ui/core.js`) upgrades an old `activeDays` array into a fully-open/fully-closed `openSlots` grid — it must run on both initial load *and* JSON import (`js/ui/io.js`), not just app startup, since an imported file can be arbitrarily old; this was a real bug (import silently skipped every migration, `constraints.groups`/`spread` included, not just this one) fixed by extracting the migration into its own method called from both places.

#### Semaine A/B

`state.volumesA`/`state.volumesB` are hours *in addition to* `state.volumes` (the common/every-week hours), scoped to plain demand only — pins/groups/meetings do **not** support alternating weeks (a deliberate v1 scope decision; extending them would need the same treatment below applied separately to each). Every session built from `volumes`/groups/pins/meetings carries `week: 'both'`; sessions built from `volumesA`/`volumesB` carry `week: 'A'`/`'B'` instead — a session's `week` never changes after construction.

The core trick that makes a slot able to alternate content is that `busyClass`/`busyProf` are **two parallel grids each** (`busyClassA`/`busyClassB`, `busyProfA`/`busyProfB`) instead of one. A `'both'` session (the common case: everything that existed before this feature) occupies *both* grids, so it blocks every week exactly like before. An `'A'`/`'B'` session occupies *only its own* grid — which is precisely what lets an `'A'` session and a `'B'` session share the same (class, day, slot) without ever being seen as conflicting, since neither one's occupancy check ever looks at the other's grid. `markClass`/`markProf`/`freeClass`/`freeProf` (in `solve()`) are the only functions that know how to translate a session's `week` tag into grid reads/writes — `candidatesFor`, `domainSize`, and the assign/undo code all go through them rather than touching the grids directly, so a fourth "week mode" would only need changes in one place. `repair()` mirrors this with a string-key suffix (`"cls|d|s|A"` / `"...|B"`) instead of a second grid, matching its existing map-based occupancy-counting style; a `'both'` item bumps both suffixes (see `weekKeys()`), an `'A'`/`'B'` item bumps only its own.

Writing the schedule cell for an `'A'`/`'B'` session uses a different shape than a `'both'` one specifically so the two are never ambiguous: `'both'` keeps the historical flat `{subj, profId, ...}` shape (nothing downstream needs to change for the non-alternating case — this is why every pre-existing rendering/export/swap code path kept working unmodified); `'A'`/`'B'` nests its cell data under `schedule[key].weekA` / `.weekB` instead, and since a `'both'` session can never share a slot with an `'A'`/`'B'` one (the dual-grid blocking above prevents it), a cell is *never* simultaneously flat and nested — `cell.weekA || cell.weekB` is a safe, unambiguous test for "this cell alternates" used everywhere (UI rendering, copy-to-text, swap exclusion). `writeCell`/`clearCell` (`solve()`) and the equivalent inline logic in `repair()`'s final schedule assembly are the only places that construct this shape.

Because `'A'`/`'B'` sessions are independent of each other and of pins/groups/meetings, the standard practical way to fill an otherwise-empty alternating slot (e.g. a subject averaging 0.5h/week, taught only every other week) is to declare a *second*, unrelated `'B'`-only (or `'A'`-only) demand — a different subject, or a generic "Étude" filler — as its own `volumesB` entry. The solver does **not** try to pair them into the same slot (a deliberate scope decision: real pairing would need a matching heuristic in the search, more complexity for a cosmetic guarantee) — each is placed independently wherever it fits, so the two *can* end up sharing a slot (visually: two boxes) but aren't guaranteed to.

Pre-checks get A/B-aware siblings rather than being folded into the existing ones, so a failure message is unambiguous about which week is the problem: `checkWeekDemand()` mirrors Check 1/2 per week label; Check 3's per-class capacity check additionally verifies `commonTotal + weekExtra <= freeCapacity` for A and B separately (a class's *physical* weekly grid is identical every week, so each week's total — common plus that week's extra — must independently fit, not just the common total alone); Check 4 gets an analogous per-week pass for a prof's *combined* (common exclusive + that week's exclusive) load against their availability, since a prof comfortable on common hours alone can still be overloaded specifically on their heavier week. `analyzeProfLoad`'s single "Charge de travail" number adds `max(exclusiveA, exclusiveB)` rather than the sum (a prof is never carrying both in the same real week) — the report exists to flag the worse of the two, not a number that could never occur in practice.

One platform gotcha worth remembering if this UI ever changes: **Ctrl+click does not fire as a normal DOM `click` event on macOS** — the OS intercepts it as a secondary-click/context-menu gesture before it reaches the page (confirmed directly via Playwright: the `click` listener never fires, `contextmenu` does instead). This is why the volumes-grid modifier scheme is Cmd+click (semaine A) / Alt+click (semaine B) rather than Ctrl+click — Cmd and Alt both fire ordinary click events with the expected `metaKey`/`altKey` flags on every platform tested.

### Solver algorithm (`js/solver.js`)

CSP solved by backtracking, structured in four phases:

1. **Pins application** — pins are hard placements applied before search; they decrement the hour demand for their (classe, matière) and mark their exact (classe/prof, day, slot) busy. Any check downstream that computes "how many free slots does X have" must net out slots already consumed by pins (via the `pinnedBusyClass`/`pinnedBusyProf` maps built here) — forgetting this was a real bug: a class/prof can look like it has enough capacity when counted against the raw weekly grid, while its *actual* remaining free slots (after pins) are already exhausted.
2. **Groups application** — a "group" (`constraints.groups`) is the flexible counterpart to a pin: N classes share the same hours of a subject (same prof, same slot) but *without* an imposed day/slot — the search still picks when. It decrements demand like a pin, and produces multi-class sessions (see below) instead of writing directly to the schedule. A class can have both grouped and individual hours of the same subject in the same run (e.g. 2h of Sport shared with another class, +1h alone) — the group only consumes the hours it declares.
2b. **Spread constraint** — `constraints.spread` marks (classe, matière) pairs where the search must never place two of that pair's sessions on the same day, without fixing which day or slot either one lands on (unlike a pin). Enforced via a `spreadKey` tag (`"cls|subj"`) carried on each affected session and a `spreadUsedDay["spreadKey|day"]` counter mutated in lockstep with `busyClass`/`busyProf` during assign/undo — a session's candidate days exclude any day another session sharing its `spreadKey` already occupies. `repair()`'s min-conflicts also tracks this (`spreadOcc`) and hard-excludes conflicting days from its candidate moves, exactly like it hard-excludes pinned cells — a constraint enforced only in `solve()` and silently droppable by `repair()` would be a correctness regression, not just a missed optimization. Pre-checked cheaply: a (classe, matière) under this rule needs at least as many open days (`openDayCount` — days with at least one open slot) as remaining hours.
2c. **Meetings** — `constraints.meetings` is the odd one out: unlike a group (which *chooses* one prof among several eligible), a meeting names an exact set of `profIds` (≥2) that are ALL mandatory simultaneously — nobody is interchangeable, so there is no "eligible profs" choice to make, only a "when" to search for. This models both a staff meeting (no class, no subject — several teachers must share a slot with nothing else to do with a class) and a co-taught course (subject + classes, decrements volume like a group, but requires several specific teachers in the room at once instead of picking one). A session's `elig` array holds exactly those required profs and a flag `allRequired: true` tells `candidatesFor`/`domainSize`/`repair()`'s candidate search to treat the (day, slot) as valid only when *every* prof in `elig` is free — one candidate per open (day, slot), not one per eligible prof, unlike an ordinary session. To make this uniform with the rest of the session-placement machinery (which already treats a placement's prof(s) as a set, not a scalar — see below), a chosen candidate always carries `profIds: string[]` (length 1 for an ordinary session, length ≥2 for a meeting); `applyDelta`/`affectedBy` accept that array directly so forward-checking recomputes every affected prof's domain, not just one. A meeting with zero classes has nothing real to key the schedule cell on, so `buildContext` invents a pseudo-class `"@meeting:<id>"` used nowhere else — `sessions`' `classes` array works completely unmodified with it, and `allSessionClasses` (config classes ∪ every class appearing in any session) is what `solve()`/`repair()` actually loop over when initializing `busyClass`, not `config.classes` directly, precisely so this pseudo-class gets its own occupancy grid like a real one. The UI (`js/ui/schedule.js`) renders a dedicated "Réunion — <name>" block for classless meetings (`UI.buildMeetingBlock`, keyed by the same pseudo-class) since `buildClassBlock`'s per-class loop will never see it; `buildProfGrid` additionally scans those pseudo-class keys so a meeting shows up in each involved prof's own view. Multi-prof cells are marked `meeting: true` and excluded from cell-swap entirely (`js/ui/swap.js`) — the swap logic assumes one prof per cell.
3. **Static pre-checks** — cheap, exact necessary conditions checked before ever searching (no prof teaches a demanded subject/group; not enough truly-free slots for a (classe, matière) pair, for a group's *shared* slot, or for a meeting's *all-required-profs-and-classes-free* slot; a class's total remaining demand — including hours it owes to groups and meetings — exceeds its truly-free weekly capacity; a prof who is the sole teacher of several subjects/groups, or who is required at one or more meetings, is overbooked across all of it combined). These exist so obviously-infeasible configs fail instantly with a precise, actionable message instead of burning the search budget to rediscover the same fact.
4. **Backtracking search** — one "session" per hour of remaining demand. A session carries `classes: string[]` (length 1 for ordinary demand, length ≥2 for a group or a meeting with several classes, or a single pseudo-class for a classless meeting) rather than a single `cls` — a multi-class session must find a (day, slot, prof-or-profs) where *every* class in it is free simultaneously, and placing it marks all of them busy at once. Uses **dynamic MRV** (the most-constrained session is recomputed every node, not sorted once up front) plus **forward-checking** (a tentative placement is rejected before recursing if it would empty another session's domain — this is what "anticipates" dead ends instead of discovering them many levels deeper). Candidate order is **always shuffled** (Fisher-Yates, every node) before the optional `options.noGapsForStudents` compaction sort is applied as a stable tie-breaker — this is not cosmetic: a fixed deterministic order (e.g. earliest-slot-first) can walk the search into an arbitrary dead branch and then reproduce that exact same failure on every single run, since nothing about the ordering ever changes. Measured on a real near-infeasible config: deterministic ordering got stuck at 30/112 placed on 5/5 identical runs, shuffled ordering reached 107–110/112. There is no setting to disable this — it was one during early development (`options.randomize`), and it was removed once this failure mode was measured, since the deterministic path had no offsetting benefit (`noGapsForStudents` compaction is fully preserved either way — the shuffle only affects tie-breaking among otherwise-equal candidates). The "avoid gaps" heuristic is evaluated against a multi-class session's *first* class only (a documented approximation — there's no single correct answer when classes' gap patterns disagree). A time+iteration budget (`options.solverTimeBudgetMs`, default 8000ms; `options.solverMaxIter`, default 60000000) guarantees the function always returns rather than hanging — on exhaustion it returns a message explicitly distinguishing **"proven impossible"** (search space fully exhausted) from **"budget exceeded, undetermined"**, and aggregates conflict frequency across the whole search to name the most likely bottleneck (classe(s)/matière + eligible profs), rather than reporting only the single deepest point reached.

**Restarts within the time budget** — a single long backtracking run, even with per-node shuffling, has heavy-tailed variance: on a genuinely hard instance the *entire* time budget can get spent thrashing near the root of the search tree, ending with a catastrophically low `deepestCount` (e.g. 31/115) on one run and 90%+ on another run of the *identical* config. `solve()` therefore splits `TIME_BUDGET_MS` into several independent attempts (`CHUNK_MS`, capped at `min(TIME_BUDGET_MS / 4, 2000ms)`, not exposed in the UI), each starting the backtracking fresh (new shuffles throughout) — `deepestCount`/`bestPlacements`/`bestMissing`/`blockedInfo` are declared *outside* the restart loop so the best result across every attempt survives regardless of which attempt found it. If any single attempt exhausts its own sub-budget without being cut short (`aborted` stays `false` for that attempt), that is a valid **proof of infeasibility for the whole CSP** independent of shuffle order — the loop stops immediately rather than wasting remaining time on further attempts that cannot change the verdict. This is a real, measured effect, not a hunch: on a hard synthetic instance (113h across 4 classes, single-teacher subjects, ~40% availability) at the real 8000ms default, single-attempt-per-budget-slice averaged 47% placed (worst 34.5%) across 8 runs, while restart-enabled solving on the identical instance averaged ~63% (worst 46%) — both better on average *and* on worst case. The chunk size matters: giving each attempt "whatever time is left" (i.e. effectively one giant attempt, no different from before) reproduces the bad variance; capping it to a real fraction of the total is what makes restarts actually happen. Don't "simplify" this by giving the first attempt the full remaining budget — that silently disables the whole mechanism while looking identical in code review.

Both the pre-checks and the search must stay consistent about what "free capacity" means once pins/groups/meetings are involved — the most common classes of solver bugs in this codebase are (a) a capacity check that forgets to subtract pinned/grouped/meeting slots, and (b) a search heuristic that's correct in isolation but changes the feasibility verdict (it must not: feasibility is a property of the CSP, not of the heuristic). When touching the session model, grep for `sess.cls` (singular) — it should no longer exist; everything is `sess.classes` (array) now, including single-class sessions. Likewise a placed candidate's prof(s) is always `c.profIds` (array, `profIds[0]` for the ordinary single-prof case) rather than a scalar `c.profId` — grep for a bare `.profId` being *assigned* from a candidate (as opposed to read for display) as a sign the multi-prof path was missed somewhere.

Phases 1–3 (pin/group application, eligibility helpers, `demand`/`groups`/`sessions` construction) live in a module-private `buildContext(state)` function, not inside `solve()` — it's the single source of truth for "how many hours does a prof have to cover, and how much is he actually free," and for the `sessions` list itself. Three functions consume it: `solve()` (the search), `analyzeProfLoad(state)` (see below), and `repair()` (see below). If you ever need a fourth place that reasons about prof load or the session list, extend `buildContext` rather than re-deriving that math again.

`Solver.analyzeProfLoad(state)` is a non-search diagnostic that reports, per prof, exclusive-hours-owed vs. net-availability-remaining, sorted tightest-margin-first (surfaced in the UI as the "Charge de travail" table on the Profs tab, recomputed on every visit to that tab since volumes/pins/groups/meetings can change elsewhere). Meeting hours count as exclusive load for every required prof unconditionally (by construction nobody else can substitute), unlike ordinary demand/groups where "exclusive" depends on how many profs happen to teach that subject. A margin of exactly 0 there is not a stable equilibrium — it means every one of that prof's free slots must be used with zero room for a class-side conflict, which in practice is close to unsatisfiable.

`Solver.repair(state, partial)` is a second, fundamentally different algorithm — local search (min-conflicts), not backtracking. `solve()` on failure now returns `{ partial: { schedule, placements, missing }, aborted }` — `schedule`/`placements` is the best valid partial assignment reached (snapshotted from an explicit `placedStack` the moment `deepestCount` improves, not reconstructed after the fact — backtracking undoes everything as it unwinds, so without that snapshot the near-solution would be lost), and `missing` is exactly which sessions didn't make it in. `repair()` seeds those missing sessions into arbitrary (but availability-respecting) slots — creating conflicts — then repeatedly moves a random conflicted session to whatever position minimizes conflicts (10% of moves are fully random, to escape local optima), until conflicts hit zero or its own time budget (`options.repairTimeBudgetMs`, default 5000ms) runs out. It is dramatically faster than exhaustive backtracking at *finding* a solution when one exists close to a near-miss (observed: an 8s backtrack timeout at 108/112 repaired to a complete, valid 126-cell schedule in ~15ms) — but unlike `solve()`, it can never prove infeasibility; a failed repair means "didn't find one this attempt," not "impossible." Both pins and already-valid placements are fair game to move during repair (moving a previously-fine session may be exactly what's needed to make room for a missing one) — only pinned cells (`pinnedBusyClass`/`pinnedBusyProf`) are permanently off-limits.

The UI (`js/ui/schedule.js`) keeps the last failed `partial` in `UI.lastPartial` (not in `state`, so a failed attempt is never accidentally persisted to localStorage) and renders it read-only (no cell-swap) below the failure message so the user sees the near-miss instead of a blank grid; the "Réparer" button is enabled exactly when `lastPartial.missing.length > 0`.

The "points de blocage" (aggregated forward-checking-wipeout/dead-end frequency) explanation is trustworthy as a *root-cause* claim only when the search actually completed (`aborted: false` — full exhaustive proof of infeasibility gives the frequency count real meaning). When the search was cut off by the time/iteration budget (`aborted: true`), that block is dropped from the message entirely — a session's dead-end count in an incomplete search often just reflects wherever the search happened to thrash, not the true global bottleneck (confirmed empirically: a prof with a comfortable +11h margin still topped the blocked list in an aborted run). Don't re-add it to the aborted branch without re-litigating that finding.
